# 问题 4：并发登录检测方案（0.3.0 历史记录）

> 以下保留 0.3.0 时的问题与改造设计。当前版本已支持不同工作目录的独立检测，验收入口为 `node scripts/test-background.mjs tests/provider-auth.test.ts`，其中覆盖工作会话与整理会话并发认证。原来要求认证相互取消的复现工具已删除。

## 当前问题与复现

现有 `ProviderAccounts.jobs` 与状态都以提供方作为唯一键。同一个 CLI 在 A、B 两个工作目录同时检测时，后发请求会取消先发请求。只去掉取消代码仍会让结果覆盖同一份状态，因此不能只修一行。

当时通过模拟 CLI 复现认证请求相互取消，不调用模型服务。0.3.0 没有把它标为已修复；以下状态表描述该历史版本，不代表当前状态。

## 推荐实现

1. **按认证上下文分开登记任务和结果。** 键由提供方、解析后的 CLI 程序路径、程序/配置代次、规范化后的工作目录组成。个人凭据变更另用递增的认证代次标记，不把密码、令牌或原始登录输出放进键。目录必须进入键，因为 CLI 可能加载目录级配置。
2. **同一键复用检测，不同键独立排队。** 同一上下文的多个窗口或 session 共用一次检测；不同上下文相互不取消。建议每家 CLI 最多同时检测 2 个、全局最多 4 个，其余显示“排队检测”。超时、重试和错误只更新对应上下文。
3. **登录流程仍按个人凭据域串行。** 同一提供方与本机账户只保留一个登录进程。登录成功或更改 CLI 配置后增加认证代次，使旧结果失效；旧请求即使迟到也不能覆盖新结果。重新检查正在使用的上下文，不中断已运行的模型任务。
4. **界面明确绑定结果。** `Snapshot.auth` 改为按上下文索引，检测响应携带上下文键和请求代次。新会话对话框只显示所选提供方和目录的结果；发送前只检查该 session 的固定上下文。关闭一个界面仅取消自己的订阅；其他调用者仍在等待时不结束公共检测任务。
5. **发送保持独立。** 点击发送时绑定 session ID、输入版本和引用列表。检测失败保留该 session 的输入；若用户切换或继续编辑，迟到结果不得清空新内容。0.3.0 已先修复这部分界面隔离。

这些是运行框架的确定性调度规则，不需要 Agent 判断，也不放进 skill。先完成任务与缓存的键改造，再改状态接口和界面；最后删除原来“同提供方新检测取消旧检测”的逻辑。

## 改造验收用例

| 用例 | 操作 | 必须满足的结果 | 当前状态 |
|---|---|---|---|
| AUTH-01 | A/B 同提供方、不同目录，同时检测 | 两个独立结果，互不取消 | 当前故障可复现，改造后验收 |
| AUTH-02 | 两个界面对相同上下文同时检测 | 只启动一次 CLI 检测，两个调用者均收到结果 | 改造后验收 |
| AUTH-03 | A 超时、B 正常返回 | A 显示超时，B 显示成功 | 改造后验收 |
| AUTH-04 | 检测途中切换目录，旧结果后返回 | 旧结果不覆盖当前目录状态 | 改造后验收 |
| AUTH-05 | 检测途中更换 CLI 或完成重新登录 | 旧代次结果被丢弃；按新配置重新检测 | 改造后验收 |
| AUTH-06 | 两个 session 同时要求登录 | 只出现一个登录进程；完成后分别复检 | 改造后验收 |
| AUTH-07 | 一个界面关闭，另一个仍在等待 | 公共检测继续；无订阅的排队检测可取消 | 改造后验收 |
| AUTH-08 | 超过并发上限后持续增加检测 | 正确排队，无无界进程增长；取消后能释放槽位 | 改造后验收 |
| AUTH-09 | B 发送等待时切到 A，B 随后失败 | A/B 输入和引用均保持各自内容 | 0.3.0 已有界面回归用例 |
| AUTH-10 | 已运行任务期间其他上下文重新检测/登录 | 运行任务不被认证调度器主动终止 | 改造后验收 |
